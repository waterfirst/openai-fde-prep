🎯 면접 로드맵 — 7단계 단계별 대응

OpenAI FDE 채용은 7-touch(레크루터 → 기술스크린 → 코딩 2회 → LLM 시스템설계 → 행동/고객공감 → 최종 가치대화)를 보통 3–4주에 압축한다. 각 라운드는 30~60분. 팀마다 순서·형식은 조금씩 다르다.

매 라운드 관통 원칙 (4개)

  • Think-aloud in English — 침묵 금지. 사고 과정을 소리내어. 정답보다 "어떻게 생각하나"를 본다.
  • Customer-first framing — 모든 답을 "고객 문제 → shipped system"으로 연결.
  • Ship & defend — 돌아가는 결과물을 내놓고, 모든 결정을 근거로 방어.
  • Clarify first — 코딩/설계 전 요구사항·제약을 먼저 질문한다.

출처: openai.com/interview-guide · Exponent/IGotAnOffer FDE 가이드(2026).

Step 1 · 30–45분 Recruiter Screen

본다: 배경·동기·미션 정렬. "Why OpenAI / Why FDE".

대응: 2분 FDE 자기소개 — "제조 26년간 애매한 현장 문제를 재현 가능한 시스템으로 바꿔왔다." 임팩트는 숫자로. 왜 지금 FDE인지 한 문장.

내 무기: 숫자 어필 · 짧은 영어

Step 2 · ~60분 (CoderPad) Technical Phone Screen

본다: 실전형 자료구조·알고리즘 (LeetCode보다 실무적).

대응: 문제 재진술 → 접근 말로 설명 → 코딩 중 계속 나레이션 → 엣지케이스. 영어 think-aloud로.

내 무기: 직접 코딩 (HashMap/Two-pointer/파일파싱 실전형)

Step 3 · 60분 ×2 Coding Rounds (product-focused)

본다: 코딩을 고객 납품물로 다루는가. 돌아가는 코드 + 실행 앱 + 명확한 워크스루.

대응: 완벽한 알고리즘보다 동작하는 결과. 모든 고객대면 결정(왜 이 자료구조/이 UX)을 즉석 딥다이브에서 방어.

내 무기: OLED 수명 웹앱 · Telegram+Codex 오케스트레이션 (실제로 배포한 것들)

Step 4 · 45~60분 LLM System Design (FDE 최난관)

본다: 프로덕션 LLM 아키텍처 · 평가 게이트 설계 · 고객 워크플로우로의 통합.

대응 치트시트:

  • RAG 결정: embedding 선택 · chunking 전략 · retrieval(하이브리드) · reranking.
  • Fine-tune vs RAG vs Prompt: 언제 무엇을. (지식 최신성=RAG, 포맷/톤=fine-tune, 소량=prompt)
  • Guardrails: PII 마스킹 · 근거 없는 답 차단 · human-in-the-loop.
  • Eval gate: 배포 전 통과 기준을 숫자로 (정확도·환각률·기대값).

내 무기: FDE 설계 템플릿 · KIS 모의투자 eval-gate 기반 자율 워크플로우 · 변호사 로컬 마스킹 → Codex → 법제처 MCP 파이프라인

Step 5 · 30~45분 Behavioral · Customer-Empathy

본다: 코드만큼 고객 공감을 본다. "고객 니즈를 shipped system으로 바꾼 경험".

대응: STAR로. 애매한 요구를 재정의하고, 신뢰를 만들고, 떠난 뒤에도 남을 자산을 놓은 이야기.

내 무기: STAR 경험은행 · 변호사 파산업무 FDE 사례 (개인정보 격리 + 고객 자립 신호)

Step 6 · 45~60분 Project Deep Dive

본다: 복잡한 시스템 하나를 골라 아키텍처를 발표하고, 빠른 꼬리질문 아래 모든 결정을 방어.

대응: 1개 프로젝트 선정 → 문제/제약 → 설계 → 트레이드오프 → 결과/측정. "내가 소유한 것"을 명확히.

내 무기: 변호사 FDE 사례(2시간 온사이트) 또는 KIS 500일 게이트 시스템 — 둘 다 재정의·설계·측정이 다 있음.

Step 7 · 30분 Final Values Conversation

본다: 미션 정렬 (AGI가 인류에 이롭게) · 안전 우선 · 협업 태도.

대응: 아부 말고 진정성. 안전·개인정보를 실제로 지킨 사례로 증명 (변호사 사건 지시-데이터 분리). 마지막에 내가 물어볼 질문 2~3개.

직접 코딩 훈련법

Codex는 무기지만, 면접장에서는 네 손이 증명서다.

  • 문제 읽고 제약조건을 먼저 묻는다.
  • brute force를 말하고 개선한다.
  • 코드는 짧고 함수형으로 쓴다.
  • edge case 3개를 직접 말한다.
  • 마지막에 complexity를 말한다.

오늘의 기본 문제

Problem: Two Sum

Input: nums, target
Output: indices of two numbers that add up to target

Approach:
1. Keep a hash map: value -> index
2. For each number, compute complement
3. If complement exists, return indices
4. Otherwise store current value

Say aloud:
“This is O(n) time and O(n) space.”

  • Workflow impact — 시간, 품질, 채택률, 재현성으로 효과를 측정한다.
  • Eval-driven feedback — 결과를 보고 모델/규칙/제품을 고친다.
  • Customer teams — 도메인 전문가와 같은 언어로 협업한다.
  • Contribute directly in code — 필요하면 직접 코딩하고 테스트한다.
  • Scope-speed-quality tradeoff — 시간이 부족하면 범위를 줄이고 품질은 지킨다.

Q. A customer gives you an ambiguous problem. What do you do?

I start with discovery and technical scoping, not immediate coding.
First, I clarify the workflow and talk to domain experts.

That is how I worked on the OLED lifetime web app.

Q. Tell me about your working style.

My working style is structured, data-driven, and field-oriented.
I am data-driven, but I also respect field experience.
In manufacturing, many important answers are hidden in the gap between data, equipment, materials, and people.
So I listen first, structure the problem, test hypotheses, and document the result.
My style is calm, persistent, and practical.

Q. What if the AI system gives a wrong answer?

I treat it as an eval and system-design problem, not just a model problem.
I check the input data, prompt, tool calls, logs, fallback logic, and evaluation criteria.

I fixed it with retry, fallback sizing, and tests.

Q. How do you work with people from different domains?

I embed closely with domain teams and translate between technical and field language.

상황대처 시나리오 — 짧게 답하는 훈련

1. 고객 요구가 모호할 때

I would not jump into implementation.
I would first clarify the workflow, success metric, data source, and user pain point.
Then I would build a small pilot and validate it with real users.

2. 시간이 부족할 때

I reduce scope, not quality.
I identify the smallest useful workflow, ship that first, and leave a clear path for expansion.
This is how I usually work with pilot-based delivery.

3. 모델이 틀릴 때

I check whether the failure is from the model, data, prompt, tool call, or evaluation.
Then I add logging and tests.
I do not want the same failure to happen twice.

4. 고객이 AI를 믿지 않을 때

I would not ask them to trust the AI blindly.
I would show small, measurable wins.
Trust comes from repeatable results, clear limitations, and human control.

5. 이해관계자가 충돌할 때

I separate facts, assumptions, and preferences.
Then I create a shared decision framework.
In manufacturing, this was often the only way to move cross-functional teams.

6. 내 코드가 실패했을 때

I first reproduce the failure.
Then I inspect logs, isolate the failing layer, write a test, and fix the smallest cause.
After that, I document the lesson.

7. 내가 모르는 도메인을 맡았을 때

I find the domain expert first.
I ask them to explain the real workflow and edge cases.
Then I translate that into a system design and validate it with a pilot.

8. 속도와 안전이 충돌할 때

I ship fast only inside a safe boundary.
For production, I use guardrails, logs, fallback, and clear human override.
Speed without control is not good deployment.

9. 영어가 막힐 때

I would slow down and say it simply.
My goal is not fancy English.
My goal is clear thinking, clear ownership, and clear communication.

10. 왜 네가 FDE에 맞는가?

Because I have spent my career solving ambiguous real-world problems.
I know how to work with domain experts, data, experiments, and constraints.
Now I want to apply that ability to AI deployment.
